# Review: feat-photo-zoom-out, all phases (1, 2)

## Should fix
- `should-fix` — **`src/model/types.ts:13`** — the doc comment on the persisted `Crop` type still says "zoom (1..8)". After this feature, the lower bound depends on the photo and the cell (`zoomLimits`, `src/model/crop.ts:19`), and the model intentionally keeps a stored zoom that is under the current limit (`tests/unit/crop.test.ts:143-155`). `Crop` is the data contract for stored albums. A future reader who adds load-time validation or a migration from this comment will reject or rewrite every zoomed-out crop.
  → change the comment to say that zoom is from `zoomLimits(...).min` (half of the whole-photo zoom, which depends on the photo and the cell) to 8, and that `clampCrop` normalises it when it is read. The file is outside the phase list, but this is a one-line change to a comment.

## Suggestions
- **`tests/e2e/crop.spec.ts:77-86`** — the wheel test gets its expected limit from `zoomLimits`, which is the code under test. Two lines later the slider test in the same file (`tests/e2e/crop.spec.ts:99-106`) and `expectedLimit` in `tests/e2e/zoom-out.spec.ts:38-47` calculate the limit independently from the brief's rule. Their comment says so: "not from zoomLimits". So the phase 1 test and the phase 2 tests use two approaches for the same value. If `zoomLimits` returns a wrong value under 1, the wheel test still passes, because the wheel stops wherever the function says.
  → use the independent formula from `crop.spec.ts:99-106` in the wheel test too. Move it to one module-level `expectedLimit(page)` in `crop.spec.ts`, so that both tests in that file use it, and drop the `CROP` import (`crop.spec.ts:7`).
- **`tests/e2e/zoom-out.spec.ts:39-55`** and **`tests/e2e/crop.spec.ts:99-115`** — the limit formula and the slider setter (`setSlider` compared with the local `set`) are copied line for line between the two specs. These copies will change together: both encode R-2 and the same "one movement = input + change" event pair. The repo has no shared e2e helper module, because each spec owns its own helpers (`export.spec.ts:21-55`, `dnd.spec.ts:12-35`). So the copy follows local convention and is not a defect. I note it because a change to the R-2 rule now needs two test edits.
  → keep each spec self-contained, as the neighbours do. If a third spec needs the same helpers, then add `tests/e2e/helpers.ts`.
- **`tests/e2e/zoom-out.spec.ts:137-147`** — the photo-to-cell drag is written inline with an 8-step loop. `tests/e2e/dnd.spec.ts:35` already has `mouseDrag(page, from, to)` for the same gesture. Per-spec convention applies again, but a named `mouseDrag` local to this spec would make the test body as short as its neighbours.
  → move the loop into a local `mouseDrag(page, from, to)` with the same signature as `dnd.spec.ts:35`.
- **`tests/e2e/zoom-out.spec.ts:199-216`** — the export test copies the ZIP path from `tests/e2e/export.spec.ts:13-55` but drops two of its checks: the wait for `export-dialog` to be visible (`export.spec.ts:45`) and the `.zip` filename assertion (`export.spec.ts:53`). Without the filename check, a change that makes the export produce a different file type fails later and less clearly, at `files['spreads/spread-01.jpg']`.
  → add `expect((await download).suggestedFilename()).toMatch(/\.zip$/)` before the unzip, as `zipOf` does.
- **`tests/e2e/zoom-out.spec.ts:228,240,241`** — the background colour `0x1d` appears four times, with three different tolerances (`< 30`, `< 10`, `> 60`) that have no names. The colour comes from `src/ui/SettingsDialog.tsx:21` (`#1d1d1d`). If that swatch changes, this test fails in a way that looks like a render bug.
  → define `const BLACK_BG = 0x1d` with a comment that points to `SettingsDialog.tsx:21`, and name the tolerances (for example `BAND_TOLERANCE`, `PHOTO_MIN_DIFF`).
- **`tests/e2e/zoom-out.spec.ts:100-101`** — `toBeCloseTo(0.5, 1)` (a tolerance of 0.05) comes just before `Math.abs(...) < 0.01`, which checks the same quantity more strictly. The first assertion can never fail when the second passes.
  → delete line 100.
- **`src/model/crop.ts:20-22`** — `zoomLimits` calculates `a = cell.w / cell.h` and the cover width `Math.min(photoW, photoH * a)` again, which `visibleSize` already calculates at `src/model/crop.ts:13-14`. Both are the definition of "zoom 1 is the cover fit". If one changes and the other does not, `min` stops being half of the whole-photo zoom. The rest of the file keeps the geometry in one place (`cellWindow` feeds both `visiblePart` and `photoBox`), so this is the one remaining copy.
  → add a private `coverWidth(photoW, photoH, cell)` that returns `Math.min(photoW, photoH * a)`, and use it in both functions. `whole` then becomes `coverWidth / Math.max(photoW, photoH * a)`.

## Verifier follow-up
- `src/ui/SpreadView.tsx:133-136` (pinch) and `src/ui/SpreadView.tsx:159` (wheel) multiply the raw stored `zoom`, not the clamped one. Before this feature the stored zoom was always in range. Now, after a border drag widens a cell, the stored zoom can be under the new limit, and the unit test at `tests/unit/crop.test.ts:143-155` keeps it there on purpose. A pinch that starts there has a dead zone: nothing moves until `z0 * dist / d0` goes above the limit. `panCrop` (`src/model/crop.ts:80`) normalises through `clampCrop` first, but these two callers do not. AC-1.20 and AC-2.17 drive the pinch and the border drag separately, so no planned check drives a pinch or a wheel after a border drag.
- `src/ui/SpreadStrip.tsx:12-15` with `src/ui/styles.css:123` (`object-fit: cover`) draws strip miniatures without the crop. Before this feature, that only hid the pan and the zoom-in. Now a zoomed-out photo appears in the strip with no background bands. No runtime check drives the strip. This is existing design and outside this feature's file list. I give it only as a tip.
