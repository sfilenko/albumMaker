## Should fix
- `should-fix` — **`tests/e2e/zoom-out.spec.ts:126-132`** — the undo test cannot catch a break in the "one slider movement is one undo step" wiring. `zoomOutFully` goes through `setSlider` (`:50-55`), which sends exactly one `input` event and one `change` event. With one `input` there is one dispatch, so one undo gives back zoom 1 even if the coalesce key is gone. Two regressions get through. (1) `CellToolbar.tsx:32` stops setting `gesture.current`, so every `input` of a real drag is its own undo step (`store.ts:43` pushes a history entry per dispatch when the key is null). (2) `CellToolbar.tsx:58` stops clearing it, so two separate movements merge into one step. The test also starts at zoom 1, the default, so an undo that resets the crop would pass too.
  → First set the slider to a value that is not 1 (for example `'2'`, one movement). Then do a movement down that sends several `input` events (for example `0.9`, `0.6`, then `'0'`) and one `change` at the end. Then do one undo and expect zoom `2`. This catches both regressions and the reset case. Because `setSlider` sends `change` after each value, it cannot send this sequence: add a variant that takes a list of values and sends `change` only after the last one.

## Suggestions
- **`tests/e2e/zoom-out.spec.ts:76-84` and `:255-263`** — `dragPhoto` and the inline `dragGutter` are the same code: a 6-step horizontal mouse drag from the centre of a test id's box. They will change together, because both copy how this suite drives a pointer drag (`spread.spec.ts:28-36` has the same loop). Helpers that each spec file keeps for itself are the convention here, so do not move this to a shared module. → In this file, make one `dragFrom(page, testId, dx)` and call it with `'cell-1-0'` and `'gutter-0'`.
- **`tests/e2e/zoom-out.spec.ts:100-101`** — `toBeCloseTo(0.5, 1)` (that is, |d| < 0.05) comes before `Math.abs(... - 0.5) < 0.01`, which is a stricter check of the same value. The first line adds nothing, and a reader can think there are two tolerances for a reason. → Delete line 100.
- **`tests/e2e/zoom-out.spec.ts:228,240,241`** — `0x1d` occurs four times. It is the black album background, `#1d1d1d` at `src/ui/SettingsDialog.tsx:21`. If that colour changes, the test fails and the message does not say why. → Put it in a named constant, for example `const BLACK_BG = 0x1d; // SettingsDialog 'black' = #1d1d1d`, and pass it into the `page.evaluate`.
- **`tests/e2e/zoom-out.spec.ts:105-111`** — the band check asserts that the cell has the computed background `rgba(0, 0, 0, 0)`. That is how the background shows through today, not what the user sees. If a later change paints the cell in the album colour, the result looks the same but this test fails. The pixel check in the export test (`:240`) already asserts the colour itself. → Keep `hitIsCell`. If you want an editor-side colour check, compare it with the spread's computed background, not with transparency.

## Verifier follow-up
- `CellToolbar.tsx:55` `step="any"`: as far as I know, Chromium and WebKit move a range input with `step="any"` by (max − min) / 100 for each arrow key. That is about 0.077 here, starting from a minimum that is not a round number, so the keyboard cannot reach exactly 1. Before this change, `step={0.1}` from `min=1` could. AC-2.18 plans to drive "the slider can be set to exactly 1". It does not say whether by keyboard. If the probe uses only a pointer or a programmatic value, nothing drives the keyboard path.
