## Verifier follow-up
- **`src/photos/originals.ts:85`** — The archive matches with the full ladder of `src/photos/match.ts:17-25`, which accepts a file with a different size. Levels 2 to 4 accept the same name and pixel size, the same stem and ratio, or the same date and ratio. `src/storage/archive.ts:211` then writes the size of that file to `album.json`. So a second choice of `IMG_0001.jpg` from the wrong folder, or a burst neighbour, gets into the archive as this photo's original, with "Оригінали знайдено" and no warning. The original of that photo is then absent from the archive, and the person cannot tell. The export can accept a close match, but an archive claims exact originals. `dup-a` and `dup-b` have different pixel sizes (`scripts/make-fixtures.mjs:16-17`), so the spec does not reach levels 2 to 4 with them, and no row of the runtime list plans a wrong file. I cannot read the Decision Log, so this may be a recorded choice.
- **`src/photos/originals.ts:45-47`** — `getOriginal` handles a missing handle and a refused permission, but not a failure of `dir.values()`. If the stored folder is gone (a moved folder or an unplugged drive), the iterator should reject with `NotFoundError`; I did not run this. `readOriginals` then rejects with no `MissingOriginalsError`, so `ArchiveDialog.tsx:74` shows a generic error, and `archive-start` repeats the same failure. The person never reaches the request for originals. `AC-2.16` and `AC-2.22` do not describe a stored folder that cannot be opened, so no check plans to drive it.
