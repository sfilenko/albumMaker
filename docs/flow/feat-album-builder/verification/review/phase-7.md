## Must fix
- `must-fix` — **`src/ui/ExportDialog.tsx:88`** — `Promise.all(files.map(candidate))` decodes every chosen original at the same time with `createImageBitmap` (`ExportDialog.tsx:44`). The import path deliberately caps full decodes at two: `mapLimit` (`src/photos/import.ts:18`) with `DECODE_LIMIT = 2` (`import.ts:9`), used at `import.ts:111`, and the module doc says "at most two decoded at the same time" (`import.ts:97`). If a user picks the originals for a whole album (say 100 camera files of 24 MP, about 96 MB per decoded bitmap), all of them are decoded in parallel. That can kill the tab, most likely on a phone, which is the device the import cap protects.
  → Export `DECODE_LIMIT` from `import.ts` and call `await mapLimit(files, DECODE_LIMIT, (f) => candidate(f))`. `mapLimit` keeps input order, and this code needs that because `matched` maps ids to indexes into `files` (`ExportDialog.tsx:89`). `candidate` already closes its bitmap on the success path and returns a fallback on a decode error, so it needs no other change to run inside the limiter.

## Should fix
- `should-fix` — **`src/ui/ExportDialog.tsx:45`** (and `:49`) — `candidate()` always sets `takenAt: null`. An EXIF reader already exists as `readTakenAt` (`src/photos/import.ts:66`, module-private), and it wrote the `PhotoMeta.takenAt` values these candidates are matched against. With `null` on every candidate, ladder level 4 (`src/photos/match.ts:24`, date plus ratio) can never match, and level 3 (`match.ts:20-23`) loses its date check. Result: a renamed original is never found in the export flow, although `matchPhotos` was written to find it.
  → Export `readTakenAt` from `import.ts` and set `takenAt: await readTakenAt(file)` in both branches of `candidate()`. It returns `null` on any parse failure and gives the same local ISO format that import stored, so the exact-equality checks in `match.ts` work without other changes.
- `should-fix` — **`src/export/export.ts:55`** — `safeName` is the second album-name sanitizer. The first is `fileName` at `src/storage/layoutFile.ts:48`, and the two give different results. `layoutFile` replaces each forbidden character with `_` (no `+`), does not trim, and falls back to `'album'` only for an empty result. `export.ts` collapses runs with `+`, trims, and then falls back. An album named `"  "` gives `export-album.zip` but a layout file named `  .album.json`. An album named `a::b` gives `a_b` in one place and `a__b` in the other. Two functions that answer one question will drift.
  → Put one exported helper (with the trim-and-fallback behaviour of `safeName`, which is the stricter of the two) in a module both files can import, and call it from `export.ts:58`, `export.ts:97` and `layoutFile.ts:48`. `layoutFile.ts` is outside this phase's file list. If that file must stay unchanged, at least export `safeName` so the later fix only touches one caller.
- `should-fix` — **`src/export/render.ts:8`** — `PRINT_DPI = 300` duplicates `DPI = 300` in `src/model/units.ts:2`. The pixel size of each file comes from `mmToPx` (`export.ts:21`, which uses `units.ts` `DPI`), and the dpi written into the header comes from `PRINT_DPI` (`render.ts:73`). The two must always be equal, or the file prints at the wrong physical size. Nothing ties them together.
  → Import `DPI` from `../model/units` and delete `PRINT_DPI`.
- `should-fix` — **`src/export/render.ts:12-27`** — `makeCanvas` repeats the OffscreenCanvas-or-`<canvas>` JPEG encoder in `scaledJpeg` (`src/photos/import.ts:82-93`): the same `typeof OffscreenCanvas` branch, the same `convertToBlob`/`toBlob` pair, and the same `new Error('toBlob failed')`. Both are "encode a canvas as JPEG on any browser" and will change together. A WebKit workaround for `convertToBlob` or a canvas-size limit has to be made in both places.
  → Move `makeCanvas` (it returns the context, so it is the more general of the two) to a shared module and rewrite `scaledJpeg` as `makeCanvas(w, h)`, then `ctx.drawImage(...)`, then `toJpeg()`. Pass the quality as a parameter, because the two callers use different values (`QUALITY = 0.95` and `PREVIEW_QUALITY = 0.85`).

## Verifier follow-up
- `src/ui/ExportDialog.tsx:93` keeps the original `photoIds` after a partial match. On the next pick, `wanted` (`:87`) again contains photos that the first pick already registered. If the user picks only the remaining files, those earlier photos appear under "Не знайдено" (`:90`), and the count at `:152` never goes down. Photos that `matchPhotos` reports as `ambiguous` are also shown as "not found". AC-7.22 drives the one-photo path. No check drives a partial pick. A fix: narrow `photoIds` to the ids not in `matched`.
- On an iPad in landscape, `desktop` is true (≥900 px), so `phone` is false (`Editor.tsx:113`) and the spreads option is offered. A spread canvas is 7157×3614 ≈ 25.9 MP (`render.ts:14`), which is more than the canvas area that WebKit allows on iOS (about 16.7 MP). No runtime row drives a WebKit spread export. AC-7.20 does not say which browser, and the e2e skips everything except Chromium (`export.spec.ts:10`).
- `zipSink` (`export.ts:72-99`) keeps every JPEG in memory, then copies them into one `Blob`. A full album (15 spreads and 30 pages at q0.95) can need several hundred MB at the peak. The no-picker path includes phones. The e2e uses a one-spread album, and the runtime list does not say how large an album AC-7.20 drives.
- `runExport` calls the folder picker (`export.ts:130`) only after it awaits `getOriginal` for every used photo (`:122-126`). When there is a stored folder handle, `getOriginal` reads the folder once per photo (`originals.ts:33`). With many photos, this can use up the click's user activation before the picker is called. AC-7.19 drives the picker, but probably only with originals already in memory.
