## Should fix
- `should-fix` — **`tests/unit/storage.test.ts:108-112`** — two of the three rejection cases cannot detect that their own check is missing. If you delete the `format` check (`layoutFile.ts:39`), `'{"format":"x"}'` still throws `LayoutFileError`, because the version check then fails. If you delete the `version` check (`layoutFile.ts:40`), the `version: 2` input still throws, because `album: {}` fails the album check. The test asserts only the class. But `reason` exists so that the interface can show a different message for each case (`layoutFile.ts:8`), and a wrong `reason` is the regression that these tests miss.
  → Assert the reason for each case, for example `expect(() => parseLayout(...)).toThrow(expect.objectContaining({ reason: 'format' }))`. Give the version case a valid album, so that only the version is wrong. Add a fourth case for `reason: 'album'`, which no test reaches now.
- `should-fix` — **`src/storage/layoutFile.ts:41-45`** — `parseLayout` checks only `id` and `spreads`, and then casts to `Album`. A file such as `{"format":"album-builder","version":1,"album":{"id":"x","spreads":[]}}` parses as an `Album` with no `name`, `settings` or `photos`. The first access to `a.settings.gapMm` or `a.photos.map` then throws a `TypeError` far from the file boundary. The user sees a crash, not the "invalid layout file" message that the `'album'` reason exists to give. The `as Album` type-checks and proves nothing about the fields that the rest of the app reads.
  → Check the other top-level fields of `Album` (`types.ts:47-56`) before the cast: `name` is a string, `photos` is an array, `settings` is an object, and `createdAt`/`updatedAt` are numbers. Throw `LayoutFileError('album')` when one fails. A deep check of each spread is not necessary for this finding.
- `should-fix` — **`src/storage/db.ts:19-28`** — `dbPromise ??= openDB(...)` caches the first promise, and that includes a rejected promise. It also caches the connection after the browser closes it. `openDB` gets no `terminated` callback, so a lost connection stays in the cache. A known case is WebKit, where the IndexedDB connection can drop after the tab goes to the background, and the project tests on mobile WebKit. After that, every `saveAlbum` fails until a reload. The autosaver retries on the next `schedule` (`autosave.ts:27`), but each retry calls the same dead connection again, so the retry cannot succeed.
  → Clear the cache on failure and on termination: `.catch((e) => { dbPromise = null; throw e; })` on the open, and `terminated() { dbPromise = null; }` in the `openDB` options. The `blocking` callback (close when a newer version opens) is not necessary while `DB_VERSION` is 1, but it goes in the same place when the version changes.
- `should-fix` — **`tests/unit/storage.test.ts:39-50`** — the `deleteAlbum` test passes if `deleteAlbum` clears the whole `previews` store, or deletes no handle. Both are plausible regressions in a function that deletes by key across three stores. `hasPreviews` (line 45) is tested only with "both copies" and "no copies". A change from `every` to `some` at `db.ts:76` passes the test.
  → Add a preview for a photo that is not in the album, and assert that it is still there after `deleteAlbum`. Add `putDirHandle(a.id, ...)` and assert that `getDirHandle(a.id)` is then `undefined`. Add a photo that has only a `full` copy to the `hasPreviews` call.

## Suggestions
- **`tests/unit/storage.test.ts:87-101`** — the failure test checks that `onError` gets the error and that a second `schedule` calls `save` again. It does not test the retry path in `autosave.ts:27` (`pending ??= a`). If you delete that line, all tests still pass. The test also does not check which album the second save got.
  → After the rejection, call `flush()` (or send `pagehide`) with no new `schedule`, and assert that `save` gets the first album again. In the existing test, assert `toHaveBeenLastCalledWith` for the second album.
- **`src/state/store.ts:55`** — `undo` sets `runKey = null`, so a coalesced dispatch after an undo starts a new history entry. No test covers this. If you delete the line, a `gutter` drag after an undo of a `gutter` drag adds no entry. The album before that drag is then not in history, and undo skips back past it.
  → Add a test: five dispatches with `coalesce: 'gutter'`, `undo`, one more with `coalesce: 'gutter'`, and then `undo` must return to the album after the first undo.
- **`src/storage/autosave.ts:9`** — the autosaver's interface is an inline object type in the signature. `store.ts:7` in the same phase exports a named `AlbumStore` interface for the same kind of factory. The test must use `ReturnType<typeof createAutosaver>` (`storage.test.ts:11`) to name the type, and every later consumer will do the same. The model files also use inline return types (`pages.ts:11`, `layout.ts:148`), but those return data and not an object with methods.
  → Export `interface Autosaver { schedule; flush; onError; dispose }` next to the factory, as `store.ts` does.
- **`src/storage/autosave.ts:46-48`** — `onError` returns nothing, but `subscribe` in `store.ts:75-78` (the same phase, the same kind of listener set) returns an unsubscribe function. A component that registers an error handler cannot remove it, and the handler keeps the component alive. Also, if no handler is registered, `autosave.ts:28` drops the error silently.
  → Return `() => errorHandlers.delete(cb)` from `onError`, as `subscribe` does. Optionally, `console.error(e)` when `errorHandlers.size === 0`.
- **`src/state/store.ts:45-49, 56-58, 65-67`** — each operation writes `past`, `future` and `album` as three separate signal writes. An `effect` that reads both `canUndo` and `album` runs between the writes and sees, for example, the new history with the old album. No effect reads these signals yet, so nothing is wrong now.
  → Put the body of `dispatch`, `undo` and `redo` in `batch(() => ...)` from `@preact/signals`. The listener loop in `set` can stay outside the batch.
- **`src/storage/db.ts:41`** — the inline `{ id: string; name: string; updatedAt: number }[]` repeats three fields of `Album`. If one of them changes type, the two declarations will not agree.
  → `Pick<Album, 'id' | 'name' | 'updatedAt'>[]`.
- **`src/storage/layoutFile.ts:25`** — `window as unknown as PickerWindow` removes all type information about `window` to add two optional members. All `PickerWindow` members are optional, so `window as Window & PickerWindow` type-checks without the `unknown` step.
  → Remove the `unknown` cast. A `declare global { interface Window { showSaveFilePicker?: ... } }` is also possible, but it is a project-wide decision, so the narrower cast is sufficient here.
- **`src/storage/layoutFile.ts:1`** — "the album without the photos" can mean "without the photo files" or "without `photos`". `serializeLayout` writes `album.photos` (the `PhotoMeta` list), so the second meaning is wrong.
  → "the album, with photo metadata but without the image files".

## Verifier follow-up
- `src/storage/autosave.ts:25-29`: two saves can be in progress together, because the timer can fire again while an earlier `save` has not settled. If the earlier save rejects after the later save starts, `pending ??= a` stores the older album, because `pending` is `null` at that time. The next `flush` or `pagehide` then writes the older album over the newer one. The comment "unless a newer change already waits" does not cover a newer change that is already in progress.
- `src/state/store.ts:14-15, 70-73`: `replace` keeps `past` and `future`. If a caller uses `replace` to open a different album, `undo` restores the previous album into the new store. The docstring does not say whether this is intended.
- `src/storage/db.ts:30, 54-56`: the preview keys use the photo id only, not the album id. If a later phase derives photo ids from the file contents, two albums share previews, and `deleteAlbum` deletes previews that another album still uses. The photo-id generation is not in this phase, so this phase cannot show which case applies.
- No runtime check plans to drive `saveLayoutFile` or `openLayoutFile` on either path. These functions also have no unit test. On mobile WebKit (an e2e target), the pickers are not present. The fallback (a detached `<a download>`, and a detached `<input type=file>` that waits for a `cancel` event) is therefore the only path on iPhone, and nothing runs it. No check plans to drive `pagehide` or `visibilitychange` saves in a real browser either.

## Summary
The store and the persistence code are compact and readable. They agree with the model layer's style: pure operations, named constants, short comments. The `idb` and `@preact/signals` usage is idiomatic. I found no helper that this code duplicates: `src/model/*` has nothing about storage or history. The real gaps are at the edges. The layout-file validation is shallow and its tests cannot see a missing check. The cached DB connection undermines the autosave retry. Several tests pass after their target line is deleted. The rest is consistency between the two factories in this phase.
